TypeScript Fundamentals

Slides: TypeScript Introduction · TypeScript Projects

Why TypeScript

  • TypeScript = JavaScript + type syntax + compile-time static typing.
  • JavaScript is dynamically typed: type errors show up only at runtime, and JS silently converts values (3 + [1] gives "31").
  • TypeScript catches those errors at compile time and refuses dubious implicit conversions.

Annotations and inference

  • Annotations (let x: number) are optional. Without one, TS infers the type: let c = [true,false] is boolean[].
  • let x = "howdy" widens to string; const x = "howdy" keeps the literal type "howdy".

The types to know

TypeKey facts
boolean, string, numberStrings are immutable; template literals use backticks and ${expr}. number covers ints, floats, Infinity, NaN; 1_000_000 separators are allowed.
bigintArbitrary-size integers, literal suffix n (10n).
enumNamed constants. Numeric values start at 0 unless set; members can be strings.
undefined vs nullundefined = absence of a value (uninitialized variables). null = a reference to nothing, assigned on purpose (Date | null).
Object typesListed property names and types. ? marks optional properties. Extra properties on an object literal are an error.
Union A | BValue is one of the types.
Intersection A & BValue must have all members of both.
Arrays T[]Mixed literals infer a union array (string|number)[]. const blocks reassignment, not mutation.
TuplesFixed length, a type per position. Must be explicitly typed (a literal alone infers an array). Support optional ? and rest ...T[] elements.
anyTurns off type checking. Avoid; useful for untyped JS libraries.
unknownType is not known. You cannot use it until you narrow it (typeof checks, as assertions).
objectAny non-primitive (objects, arrays, functions). Primitives are errors.
Common trap: any vs unknown. Both accept any value, but only any lets you call methods on it without checking.

Structural typing

Compatibility depends on shape (property names and types), not the declared name. Two unrelated classes or a plain object literal are interchangeable if their public members match.

Type aliases

type Age = number; names any type for reuse: primitives, object shapes, unions.

Functions

  • Four forms: named function, function expression, arrow function, shorthand arrow (implicit return).
  • Return type can be inferred. void when nothing is returned.
  • Optional p?: T, default p = 5, rest ...nums: number[].
  • Function types: type EventReceiver = (evt: Event) => boolean;. Parameter names are not part of the type. Used for callbacks.

Projects, modules, declaration files

  • Setup: npm init --yes → npm install typescript @types/node --save-dev → npx tsc --init.
  • tsconfig.json: target (JS version, ESNext), module (commonjs), outDir (dist), sourceMap (maps JS lines back to TS for debugging), include (["src"]).
  • tsc outputs source code, not bytecode, so it is called transpiling.
  • A file with a top-level import/export is a module with its own scope; without one it is a script in global scope.
  • Export: export class X or export { a as b }. Import: named import { A } from "./a", renamed { A as B }, namespace import * as people from "./person".
  • .d.ts files give type info for plain JS libraries (like C headers). They enable autocomplete, and tsc can generate them from your TS.

TypeScript Classes and Interfaces

Slides: TypeScript Classes and Interfaces (chess example)

Classes

  • Default member visibility is public. Also private, protected (subclasses only), readonly.
  • Parameter properties: constructor(private file: File, private rank: Rank) declares and assigns fields in one step.
  • abstract class Piece cannot be instantiated. abstract canMoveTo(p): boolean has no body; subclasses must implement it. A protected constructor means only subclasses can call it.
  • class King extends Piece: single inheritance only. super(...) calls the parent constructor or methods.
  • static members are called on the class (Game.makePieces()).
  • Accessors: get age() / set age(v) backed by _age; the setter can validate and throw.
abstract class Piece {
  protected position: Position;
  protected constructor(private readonly color: Color, file: File, rank: Rank) {
    this.position = new Position(file, rank);
  }
  moveTo(position: Position) { this.position = position; }
  abstract canMoveTo(position: Position): boolean;
}
class King extends Piece {
  constructor(color: Color, file: File, rank: Rank) { super(color, file, rank); }
  canMoveTo(position: Position) {
    const d = this.position.distanceFrom(position);
    return d.rank < 2 && d.file < 2;
  }
}

Interfaces vs type aliases

interfacetype
Can describeObject shapes onlyAnything: primitives, unions, intersections, objects
Extendinginterface Sushi extends Foodtype Sushi = Food & {…}
Conflicting member when extendingCompile error (TS2430): stricter checkingIntersection silently produces an unusable member
Declared twiceDeclarations mergeDuplicate identifier error (TS2300)
  • A class can implements zero or more interfaces and extends zero or one class.
  • instanceof checks class ancestry at runtime. It cannot check interfaces, because interfaces don't exist at runtime.
  • readonly works on class, interface and type fields; readonly number[] blocks push and index assignment.
  • Private/protected members make structural compatibility stricter: the member must come from the same declaration.

React Fundamentals

Slides: React Fundamentals

What React is

  • A JS library for building single-page applications from reusable components.
  • Key ideas: component-based architecture, virtual DOM (minimizes direct DOM manipulation), unidirectional data flow (parent → child via props).
  • The DOM is the browser's live tree representation of the page; scripts read and change it.

Traditional web app vs SPA

TraditionalSingle-page app
Every action sends an HTTP request; server returns a whole new HTML page.First request returns the app (HTML + JS). JS updates the DOM locally.
Heavy server load, idle browser, latency, sluggish UI.When data is needed, JS calls a web API (usually JSON) and updates only part of the DOM.

Components, JSX, props

  • A component = a function returning JSX plus the logic/event handlers it needs.
  • JSX is HTML-like syntax that a transpiler (Babel) turns into React.createElement(type, props, ...children). Files: .jsx / .tsx.
  • A component must return one root element; use a fragment <>…</> to avoid an extra div.
  • Props are typed with an interface and passed like attributes: <UserItem value={user} />.
  • Vite project: index.html host page → src/main.tsx initializes → src/App.tsx root of the component tree.
interface Props { value: User; }
const UserItem = (props: Props) => (
  <div><img src={props.value.imageUrl} /> {props.value.alias}</div>
);

Conditional rendering

  • If/else: {isAuthenticated() ? <AuthenticatedRoutes /> : <UnauthenticatedRoutes />}
  • If-only: {!displayedUser.equals(currentUser) && <Link…/>}
  • Guard: return <></> when required values are null.
  • Helper functions can return JSX (JSX.Element).

React Hooks and State

Slides: React Hooks · React State

Hook rules

  • Hooks give functional components features that used to need class components, and let you reuse logic without inheritance.
  • Names start with use. Call them only from functional components or other hooks.

useState details

  • Regular local variables are re-initialized on every render; state survives.
  • Prefer the functional updater to avoid stale values: setItems(prev => [...prev, ...newItems]).
  • Updating one field of an object: setInfo(prev => ({ ...prev, displayedUser: user })).

Context in three steps

  1. export const UserInfoContext = createContext<UserInfo>(defaultUserInfo);
  2. Write a Provider component that holds the state and supplies values/functions.
  3. Wrap it around every component that needs it (Tweeter nests the providers in index.tsx), then read with const { updateUserInfo } = useContext(UserInfoContext);

Router hooks

  • useNavigate → navigate function. useLocation → location.pathname.
  • useParams → { displayedUser } for feed/:displayedUser. useSearchParams → [searchParams, setSearchParams]; searchParams.get("page").

Custom hooks

A function named useX that calls other hooks and returns values/functions (Tweeter's useMessageActions wraps useContext(ToastActionsContext)). Reasons: reuse, abstraction, separation of concerns (SRP), testability, sharing across projects.

Common trap: useCallback memoizes a function, useMemo memoizes a value. Tweeter uses both together: functions wrapped in useCallback, grouped into an object wrapped in useMemo.

Modeling and UML

Slides: UML Class Diagrams · plus sequence diagram exercise

Models

  • A model is an abstraction of a system from a chosen viewpoint and level of abstraction. Modeling manages complexity by ignoring irrelevant detail.
  • Why model software: visualize/understand it, document and communicate the design, guide construction.
  • Three ways to use UML: sketch (agile, informal), blueprint (big design up front), programming language (code generation, 1990s).
  • Levels: conceptual (understand the problem) → high-level design → low-level design → implementation (do that in code, not UML).
  • Structural diagrams: class, package, object, component, deployment. Behavioral: use case, state, activity, communication, sequence.

Sequence diagrams (exercise / review sheet)

  • Participants across the top, each with a dashed vertical lifeline; time flows down.

Software Architecture

Slides: Software Architecture · Dr. Rodham's Software Architecture

Definitions

  • Software architecture: the large-scale organization of software into subsystems, packages and layers: the major parts, their responsibilities, how they communicate, and why.
  • Design levels: System → Subsystems → Packages (high-level) → Classes → Methods (low-level).
  • Layer: a coarse, horizontal grouping with cohesive responsibility at one level of abstraction. Subsystem: a vertical slice of functionality (Billing, Inventory).
  • Package: a code-organization unit (Java package, namespace). Component: a replaceable unit that hides its implementation behind interfaces.
  • Layer = logical; tier = physical (separate machine/process).
  • Architecture defines: subsystems, their responsibilities, dependencies, interfaces, communication, technologies, physical deployment.

Layered architecture

  • Higher layers depend on lower layers; lower layers never depend on higher ones.
  • Strict: depend only on the layer directly below (network stacks). Relaxed: depend on any lower layer (business apps).
  • Scenario I: request travels down and fans out; results combine on the way up (TCP/IP). Scenario II: Layer J answers without going lower (caching). Scenario III: events travel up from Layer 1 (interrupts, async I/O).
  • Common layers, top → bottom: UI / communication endpoints → use cases / business logic → domain model / entities → frameworks, libraries, DBs → OS → hardware. Lower = more general and reusable.
  • Errors: a layer's interface includes its errors; map lower-level errors to your layer's abstraction so they don't leak upward.

Benefits vs drawbacks

BenefitsDrawbacks
Separation of concerns · lower coupling · higher cohesion · reuse of lower layers · replaceable layers · clarity · distribution across servers · parallel team workEfficiency overhead crossing layers · changes can ripple to adjacent layers (more layers if relaxed) · some dependencies are forbidden

Coupling = how much one element depends on others (minimize). Cohesion = how related an element's operations are (maximize).

Diagrams

High-level: component diagrams (subsystems + dependencies) and package diagrams (nested packages, dependencies as dashed arrows pointing downward). Low-level: class diagrams.

Design Patterns and Observer

Slides: Observer · reading: GoF Ch. 1 and Observer

How to study any pattern (from the review sheet)

  • Intent / the problem it solves
  • Structure: the classes, interfaces and relationships, and why each is there
  • When you'd use it and what it buys you
  • Be ready to write it in TypeScript

Observer

  • Problem: objects (observers) need to know when another object (the subject) changes state, so they can stay in sync or react.
  • Solution: the Subject keeps a list of Observers and offers attach/detach. When its state changes it calls notify(), which calls update() on every Observer. Observers depend only on an interface.
  • Consequences: observers can be added/removed freely; subject isn't coupled to concrete observers (an example of dependency inversion); supports broadcast; but a state change can trigger an unexpectedly expensive cascade of updates.
  • Known uses: keeping views in sync with data, session login/logout listeners, history (browser URLs, undo/redo).
  • Java historically had Observer.update(Observable, Object) and Observable.addObserver / deleteObserver / notifyObservers.
interface Observer { update(subject: Subject): void; }

abstract class Subject {
  private observers: Observer[] = [];
  attach(o: Observer) { this.observers.push(o); }
  detach(o: Observer) { this.observers = this.observers.filter(x => x !== o); }
  protected notify() { this.observers.forEach(o => o.update(this)); }
}

class FlightFeed extends Subject {
  private _flight: Flight | null = null;
  get flight() { return this._flight; }
  set flight(f: Flight | null) { this._flight = f; this.notify(); }
}

class StatusObserver implements Observer {
  update(subject: Subject) {
    const f = (subject as FlightFeed).flight;
    if (f) console.log(`${f.callsign} at ${f.latitude}, ${f.longitude}`);
  }
}

Push vs pull: the code above is pull (observer reads what it needs from the subject). A push variant passes the changed data in update(data).

User Interface Architecture

Slides: User Interface Architecture · reading: MVC, MVP, MVVM

Underlying principles

  • Keep Model code and UI code separate: more understandable, more maintainable (they change for different reasons, see SRP), more reusable (one model, many UIs), and teams don't step on each other.
  • Inside the UI, keep display code (views) separate from input-processing code (controllers/presenters/view models). Display code is hard to test automatically; input code is easy, so separating them maximizes testable code.
  • The Model implements Observer so the UI learns when data changes.

MVP vs MVC

MVP moves deciding what to display, fetching it from the Model, and observing the Model out of the View into the Presenter. Advantage: more logic sits in the Presenter, which doesn't depend on the UI framework and is easy to unit test; the View loses its Model dependency. Cost: the View interface grows (setters as well as getters) and the Presenter does more work.

MVVM vs MVP

MVVM replaces method calls between View and Presenter with framework-managed data binding. The ViewModel "models the view": its properties map to displayed values and UI state (isSaveEnabled, message), its methods map to user actions. Advantage: much less glue code, and non-programmer designers can build views declaratively. Cost: you depend on a binding framework, and binding behavior can be harder to trace and debug.

MVP in React (Tweeter)

A functional component can't implements an interface, so it builds a const listener: UserInfoPresenterView = { setIsFollower, … } from its state setters, passes it to the Presenter's constructor, and stores the Presenter in useRef so it's created only once.

const listener: UserInfoPresenterView = {
  setIsFollower, setFolloweeCount, setFollowerCount,
  displayErrorMessage,
};
const presenterRef = useRef<UserInfoPresenter | null>(null);
if (!presenterRef.current) presenterRef.current = new UserInfoPresenter(listener);
